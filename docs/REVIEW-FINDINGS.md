# نتائج المراجعة (لم يتم التحقق منها بعد)

هذه نتائج المراجعين قبل انتهاء حدّ الجلسة. لم تمر بمرحلة التحقق المستقل، لذا يجب التأكد من كل بند قبل إصلاحه.

## SEC

### SEC-01 [high] Editors can read every manager-only discount code, and publish it, by linking it to an offer by numeric id
- الملف: `backend/app/content/offers.py`:124
- الوصف: Discount codes are meant to be manager-only: GET/POST/PATCH /admin/discounts use require_manager, and tests/test_content_admin.py::test_editors_cannot_touch_discounts_or_settings checks this. But POST and PATCH /admin/offers only use require_editor and accept any `discount_code_id`. `_check_discount_exists` (offers.py:124, called at :136 and :149) only checks that the id exists. It does not check the actor's role or whether the code is active or meant to be advertised. The response `OfferAdminOut.from_row` (admin_schemas.py:242) then returns `discount_code=offer.discount_code.code` in clear text, inactive codes included. The admin UI even tells editors to type the numeric id (frontend OfferEditor.tsx DiscountField). Ids are sequential BIGINTs, so an editor can walk ids 1..N and read every code. An editor can also set is_active/show_banner on the offer, so the public GET /offers?banner=true shows the code to everyone once it is usable.
- سيناريو الفشل: Proven with a scratch test on the throw-away test DB. A manager creates an inactive single-use 100%-off code 'VIP-FREE-100'. An editor gets 403 on GET /admin/discounts. The same editor sends POST /admin/offers {slug:'test-probe', discount_code_id:1, is_active:false} and gets 201 with "discount_code":"VIP-FREE-100". After the code is active, the editor sends PATCH {is_active:true, show_banner:true}. Public GET /api/v1/offers?banner=true then returns discount_code 'VIP-FREE-100' to every visitor. Result: free reports and lost revenue, and the editor/manager role boundary is bypassed.
- الإصلاح المقترح: Make linking a discount a manager action. In content/admin_router.py create_offer/update_offer, pass the actor through. If the actor's role is EDITOR and `discount_code_id` is set or changed, raise ApiError(403,'forbidden'). For editors, have OfferAdminOut leave the code out (or show only `_usable_code(...)` for an already-linked, live code). Also consider an explicit manager-set `advertisable` flag on DiscountCode, and allow only such codes on offers.

### SEC-02 [medium] max_redemptions is not enforced atomically: a single-use 100%-off code can be redeemed many times by concurrent requests
- الملف: `backend/app/payments/service.py`:147
- الوصف: `pricing.quote` (pricing.py:83) checks `redemptions_count >= max_redemptions` on an unlocked read. For a fully discounted order, `create_order` (orders/service.py:108-114) then confirms payment in the same request through `_confirm_free_order` -> process_event -> confirm_payment -> `_count_redemption`. `_count_redemption` (service.py:151-156) increments the counter without any condition. Concurrent requests all pass the check before any of them commits, and each one adds 1. Nothing re-checks the limit, so every request gets a free order queued for generation (6 Gemini calls plus a PDF each). The comment that a paid order is honoured after the code runs out makes sense for real payments, but not for the 0-amount path, where no money changes hands.
- سيناريو الفشل: Proven with a scratch test on the throw-away test DB. Discount ONCE100 (percent 100, max_redemptions=1). Six threads call create_order at the same moment with that code. Result: all 6 orders are 'queued', amount_cents=0, redemptions_count=6. With the X-Forwarded-For spoof in SEC-03, the per-IP order limit (20/h) does not cap this either.
- الإصلاح المقترح: For free orders, enforce the limit under a lock. In create_order, when price.amount_cents == 0 and a discount is used, `SELECT ... FOR UPDATE` the discount_codes row, re-run `rejection_reason`, and only then confirm. Or make `_count_redemption` a conditional `UPDATE discount_codes SET redemptions_count = redemptions_count + 1 WHERE id=:id AND (max_redemptions IS NULL OR redemptions_count < max_redemptions) RETURNING id`, and when no row comes back on the FREE_PROVIDER path, raise invalid_discount('exhausted') so the transaction rolls back.

### SEC-03 [medium] Every per-IP rate limit can be bypassed: the client chooses its X-Forwarded-For in the shipped deployment (TRUSTED_PROXY_HOPS=0)
- الملف: `backend/app/utils.py`:24
- الوصف: `client_ip` trusts the first X-Forwarded-For entry (trust_proxy_headers defaults to True, config.py:76). The Next.js proxy is supposed to replace the header with one trustworthy address (ARCHITECTURE §8). But the Dockerfile (line 25) and docker-compose.yml (line 65) ship TRUSTED_PROXY_HOPS=0. In that mode forwarded.ts:23-25 uses the last entry of the header the browser sent, and Next.js only fills the header when the client sent none. So the client chooses the address the API sees. forwarded.ts admits this in a comment, but nothing enforces the reverse proxy it asks for. Affected: order create/checkout (20/h), free reading (30/h), the discount-code quote oracle (60/h; it also reveals whether inactive or expired codes exist), report download (30/min), city search, and the admin login per-IP cap (30/15 min). It also feeds the memory growth in SEC-06.
- سيناريو الفشل: Proven on the dev stack. Two POSTs to http://localhost:3000/api/v1/admin/auth/login with headers 'X-Forwarded-For: 203.0.113.7' and then '198.51.100.9' (wrong password, email test-xff-probe@example.com). In login_attempts.ip the API recorded exactly 203.0.113.7 and 198.51.100.9. A script that changes the header on every request is never rate-limited.
- الإصلاح المقترح: Do not ship hops=0 as a deployable default. Add a reverse proxy (Caddy/nginx) to docker-compose that overwrites X-Forwarded-For with $remote_addr, and set TRUSTED_PROXY_HOPS=1 in the Dockerfile and compose. Make the web server refuse to start with NODE_ENV=production and TRUSTED_PROXY_HOPS=0, or ignore the client header entirely in that mode. In the backend, take the rightmost X-Forwarded-For entry (the one the trusted hop added) instead of [0], and default trust_proxy_headers to False unless it is explicitly set.

### SEC-04 [medium] Admin login throttle is check-then-act: concurrent guesses get past the 5-failures-per-email limit
- الملف: `backend/app/admin_auth/service.py`:195
- الوصف: `authenticate` counts recent failures (`check_login_throttle`, line 195), then runs argon2 (line 198), and only after that records the failure (`_record_failure_and_raise`). The failure row is committed by the router after the request. No lock spans check, verify and record. Every request that arrives before the first failure is committed sees zero failures and gets its password (or TOTP code) checked. The same pattern applies to change_password (line 223) and disable_mfa (line 263). Bursts of about 30-40 requests (the API threadpool and DB pool size) are evaluated in each 15-minute window instead of 5. That is roughly 8x the documented password-guessing rate, and for an attacker who already has the password, 8x the TOTP-guessing rate.
- سيناريو الفشل: Proven with a scratch test on the throw-away test DB: 30 threads call service.authenticate for one owner email with 30 different wrong passwords at the same moment. Result: {401: 30}. All 30 guesses were checked and none got 429, although MAX_FAILURES_PER_EMAIL=5. Sending a burst of this size every 15 minutes keeps getting about 30 guesses per window.
- الإصلاح المقترح: Serialise attempts per email inside the request transaction. As the first statement of authenticate, change_password and disable_mfa, run `db.execute(text('SELECT pg_advisory_xact_lock(hashtext(:k))'), {'k': 'login:' + email})`. The router already commits the failure row before re-raising, which releases the lock, so the next attempt sees the new failure. Optionally do the same per IP. Another option is to insert the failed-attempt row before verifying the password and mark it as success afterwards.

### SEC-05 [medium] A live owner session cookie is committed to the repository (frontend/owner.jar)
- الملف: `frontend/owner.jar`:5
- الوصف: frontend/owner.jar is a curl cookie jar that is tracked in git, added in commit 1ef4d71 'Add admin dashboard'. It holds a `zb_admin` session token for 127.0.0.1 that expires 2026-10-07 02:17 UTC. Session tokens give full admin access without a password or MFA. Anyone who can read the repository, a fork or a CI log can impersonate the owner on that stack until it expires. The frontend Docker build context also includes the file, because it is not in .dockerignore (the final standalone image does not copy it).
- سيناريو الفشل: Checked read-only: GET http://127.0.0.1:8000/api/v1/admin/auth/me with 'Cookie: zb_admin=<token from owner.jar>' returns 200, so the shared dev owner session is still valid. With it, someone could create admin users, change settings, read all orders and customers' personal data, and so on.
- الإصلاح المقترح: Remove frontend/owner.jar from the tree (and from history if the repo is shared). Revoke the session: delete its admin_sessions row or log out with it. Add `*.jar`, `cookies*.txt` and `*.cookie` to .gitignore and frontend/.dockerignore. Keep scratch curl cookie jars under /tmp.

### SEC-06 [medium] The in-process rate limiter never evicts keys: unbounded memory growth, and each IPv6 address counts separately
- الملف: `backend/app/ratelimit.py`:25
- الوصف: `RateLimiter._hits` is a defaultdict(deque). Old timestamps are popped, but a key is never deleted, even when its deque is empty, so every distinct `<scope>:<ip>` stays for the life of the process. I measured about 894 bytes per key. Keys come from client_ip: any value can be chosen via X-Forwarded-For (SEC-03), and IPv6 clients can rotate through a /64 prefix even with correct IP handling. Rotating addresses defeats every limit and grows API memory without bound.
- سيناريو الفشل: Measured with a scratch script: 200,000 hits on unique keys left 200,000 entries in RateLimiter._hits, about 894 bytes each. 1M requests to the cheap GET /api/v1/geo/cities, each with a different X-Forwarded-For, add about 900 MB to the API worker. The process is never cleaned up and is eventually OOM-killed. Each spoofed address is also within its own limit, so no request is throttled.
- الإصلاح المقترح: In hit(), when q is empty after pruning and no hit is added, delete the key. Also add a periodic sweep, or use a bounded TTL/LRU map such as cachetools.TTLCache(maxsize=...), so the number of keys is capped. Key IPv6 addresses by their /64 prefix. For multiple instances, move the limiter to Redis or the reverse proxy.

### SEC-07 [low] Prompt templates: the sandbox blocks Python internals, but there are no resource limits, and runtime errors other than TemplateError escape
- الملف: `backend/app/generation/templating.py`:110
- الوصف: Checked: the SandboxedEnvironment (Jinja2 3.1.6, which includes the str.format and |attr bypass fixes) blocks __class__, __globals__, __init__ and similar. Managers cannot reach Python internals. However: (1) The plain SandboxedEnvironment intercepts no binary operators and allows nested range() loops of 100k each. '{% for a in range(100000) %}{% for b in range(100000) %}{% endfor %}{% endfor %}' runs about 1e10 iterations (9M took 0.44 s), and `{{ 'a' * 10**10 }}` tries to allocate 10 GB. This hangs or OOM-kills the API at preview/save time, or the worker on every order. (2) render_prompt only catches TemplateError. ZeroDivisionError, OverflowError, TypeError and ValueError escape, giving a 500 instead of 422 invalid_template. Templates whose errors depend on the data pass `validate_template`, which renders only once with the sample values (name 'Alex', sun_degree 24.3). Example: `{{ 1/(sun_degree|int - 25) }}` or `{{ name[3] }}`. Such a template then fails real paid orders in jobs.py:198: generic exceptions are retried until max_attempts and the order ends in generation_failed.
- سيناريو الفشل: A manager publishes `{{ name[3] }}` in slot 1. It validates, because 'Alex' has 4 characters. Every customer whose display_name is empty or shorter than 4 characters raises UndefinedError, so slot 1 hits PermanentJobError and the paid order goes to generation_failed. Separately, preview with the nested range template blocks an API thread for minutes.
- الإصلاح المقترح: Subclass SandboxedEnvironment: set intercepted_binops={'*','**'} and override call_binop to limit operand and result sizes, and replace the `range` global with a version capped at a small maximum (for example 1000). Cap template length and rendered output length. In render_prompt, catch `Exception` (not only TemplateError) and wrap it in PromptTemplateError. In validate_template, render with several variable sets (empty name, long name, degree edge values 0 and 29.9, every animal/sign) so data-dependent failures are caught when the template is saved.

### SEC-08 [low] NUL bytes and out-of-range integers in public/admin inputs cause unhandled 500s (outside the JSON error contract, logged with parameters)
- الملف: `backend/app/content/router.py`:37
- الوصف: Several request fields reach PostgreSQL without `reject_nul` or BIGINT bounds, and psycopg's DataError is not mapped to an ApiError. Affected: SlugParam on /blog/{slug}, /offers/{slug} and /library/{slug} (content/router.py:37); `discount_code` in QuoteIn/OrderCreate (orders/schemas.py:54); LoginEmail (admin_auth/schemas.py:46); `city_id: int` on GET /geo/cities/{city_id} (geo/router.py:47); `version_id: int` on the admin prompt routes. All of them answer with plain-text 'Internal Server Error' 500 instead of the documented JSON error. Outside production, the traceback is logged with the bound SQL parameters (e.g. the login email), because hide_parameters is only enabled in production.
- سيناريو الفشل: Checked with curl against the dev API: GET /api/v1/blog/%00ab, /offers/%00x, /library/%00x -> 500. POST /api/v1/orders/quote {"discount_code":"A\u0000B"} -> 500. POST /admin/auth/login with email 'test-\u0000x@example.com' -> 500. GET /api/v1/geo/cities/99999999999999999999 -> 500. /tmp/zb-logs/api.log contains '[parameters: {'email_1': 'test-\x00x@example.com', ...'.
- الإصلاح المقترح: Add AfterValidator(reject_nul) to SlugParam, the discount_code fields, LoginEmail and the geo search query, and give path ids bounds (Path(ge=1, le=2**63-1)). As a safety net, register an exception handler for sqlalchemy.exc.DataError that returns 422 validation_error JSON.

### SEC-09 [low] Production safety checks are opt-in: ZB_ENV defaults to development, and the 'single-server deployment' compose file runs with it
- الملف: `backend/app/config.py`:26
- الوصف: Every production guard depends on ZB_ENV=production: the Secure cookie, a real ZB_IP_HASH_SECRET, rejecting the fake payment/AI providers, hide_parameters (db.py:25), and turning off /api/docs and openapi.json. `env` defaults to 'development', and docker-compose.yml, described as a 'Local / single-server deployment', loads backend/.env.example, which sets ZB_ENV=development. Someone who deploys that stack with Stripe and Gemini keys gets no production checks and no warning. Admin cookies lack the Secure flag, IP pseudonyms use the public dev secret (reversible), the OpenAPI schema is public, and 500 tracebacks log customer emails and birth data as SQL parameters.
- سيناريو الفشل: An operator follows docker-compose.yml for a single VPS behind TLS and sets only ZB_PAYMENT_PROVIDER=stripe plus the Stripe and Gemini keys. The API starts with no error. Set-Cookie zb_admin has no Secure flag, /api/docs is reachable, and ip_hash uses 'dev-only-ip-hash-secret'.
- الإصلاح المقترح: Fail closed. Require ZB_ENV with no default (or default it to 'production'), and use a separate env file for local development. Always set create_engine(hide_parameters=True) unless an explicit debug flag is on. Have the compose file read a deployment env file that ships with ZB_ENV=production.

## PAY

### PAY-01 [high] Refunding a duplicate payment revokes the customer's report even though their real payment is still captured
- الملف: `backend/app/payments/service.py`:180
- الوصف: `confirm_payment` sees a second, different payment for an already-paid order and only returns `duplicate_payment` (line 116-119). Its log line says to "refund the second payment". But `refund_order` (lines 170-187) never compares the refunded charge's payment id with `order.provider_payment_id`. Any full `charge.refunded` event that resolves to the order sets it to REFUNDED, expires the report and clears the email token. The event resolves through `_resolve_order_id`, which uses the charge metadata order_id first. That metadata is copied from `payment_intent_data.metadata`, the same mechanism the code relies on for normal refunds.
- سيناريو الفشل: Proven with a scratch test against the real webhook endpoint. A customer pays twice: session cs_test_1/pi_first, then cs_test_2/pi_second. The second payment is recorded as `duplicate_payment`. Ops follow the log and refund pi_second in Stripe. The resulting `charge.refunded` (metadata order_id, payment_intent=pi_second) is processed as `refunded`. The order becomes REFUNDED, the download is revoked and cleanup deletes the PDF. The customer's pi_first payment is still captured, so they paid and have no report. The duplicate payment itself also raises no alert.
- الإصلاح المقترح: Pass `event.provider_payment_id` into `refund_order`. When the order already has a `provider_payment_id` and the refunded payment id differs, return a new outcome such as `duplicate_payment_refunded` and leave the order and report alone. Only revoke when the ids match, or when the order has no stored payment id. Add a regression test for the duplicate-then-refund sequence.

### PAY-02 [high] Gemini or SMTP outage of about 75 seconds permanently fails every paid order, with no alert or automatic recovery
- الملف: `backend/app/payments/service.py`:162
- الوصف: `generate_report` is enqueued with the default `max_attempts=5` (queue.py line 33). `mark_failed_attempt` backs off 5/10/20/40 s with plus or minus 25% jitter (queue.py lines 102-103). On the 5th transient `AITransientError` (503 overloaded, 429 quota, timeouts), `handle_generate_report` marks the order `generation_failed` (generation/jobs.py lines 84-87) and the job fails permanently. Nothing re-queues these orders, and nothing notifies anyone: there is no alert code in the backend. Meanwhile the customer page says "Our team has been notified and will resolve it" (frontend messages en/ar `generation_failed`). `send_report_email` uses the same 5-attempt budget, so an SMTP outage longer than about 75 s permanently drops the delivery email.
- سيناريو الفشل: Proven with a scratch test using `worker.run_once` and an AI client that always raises `AITransientError(503)`. The observed backoffs were [5, 10, 20, 40] s, then job=failed with attempts 5 and order=generation_failed. In production: Gemini returns 503 "model overloaded" or 429 daily-quota errors for an hour. Every order paid in that hour fails about 1-1.5 minutes after payment, and the paying customers wait indefinitely. An admin must find and retry each order by hand, because there is no bulk retry and no sweep.
- الإصلاح المقترح: Give transient AI and SMTP failures a time-based retry budget instead of 5 quick attempts. For example, enqueue generate and email jobs with a larger `max_attempts` (about 20) and cap the backoff at 10-15 minutes, for a window of at least 6-12 h. Alternatively, do not count `AITransientError` toward the budget until `now - paid_at` exceeds a configured limit. Add a periodic sweep that re-queues `generation_failed` orders whose `last_error` starts with `ai_unavailable`. Notify ops by email or dashboard when an order enters `generation_failed` or an email job fails, and add a bulk "retry failed generation" admin action.

### PAY-03 [medium] Concurrent orders overspend limited discount codes: a single-use 100% code gives unlimited free reports
- الملف: `backend/app/orders/pricing.py`:83
- الوصف: `max_redemptions` is enforced only by an unlocked read in `quote()` (`redemptions_count >= max_redemptions`). `_count_redemption` (payments/service.py lines 147-156) then increments unconditionally. For free orders, `create_order` runs the quote check, chart computation, order insert and redemption in one request. Concurrent requests all read the old count before any of them commits. For paid codes the limit is never re-checked at payment either, so any number of orders created while the count is below the limit are all honoured.
- سيناريو الفشل: Proven with a scratch test. A code FREE1 with 100% off and `max_redemptions=1` received 6 concurrent `POST /api/v1/orders` requests. All 6 returned 201 and all 6 orders are `free`/queued. `redemptions_count` ended at 6. Each order costs 6+ Gemini calls and a PDF. A "first N customers free" giveaway is unbounded for anyone who scripts parallel requests: the per-IP limit is 20 per hour and multiple IPs can be used.
- الإصلاح المقترح: Make redemption atomic and conditional: `UPDATE discount_codes SET redemptions_count = redemptions_count + 1 WHERE id=:id AND (max_redemptions IS NULL OR redemptions_count < max_redemptions) RETURNING id`. For free orders, raise `invalid_discount('exhausted')` and roll back when no row is returned. Alternatively, lock the discount row (`SELECT … FOR UPDATE`) in `create_order` before the quote and keep the lock until commit. For paid orders, consider reserving a redemption at order creation and releasing it on abandon or expiry, so limits cannot be exceeded by outstanding unpaid orders.

### PAY-04 [medium] A refund processed before its payment event is lost, and the refunded payment still gets a report
- الملف: `backend/app/payments/service.py`:177
- الوصف: `refund_order` returns `not_refundable` for an AWAITING_PAYMENT or ABANDONED order and stores nothing that `confirm_payment` checks later. The refund event row is consumed (unique per event_id), so Stripe will not redeliver it. Stripe explicitly does not guarantee event ordering, and failed deliveries are retried on independent schedules. When the `checkout.session.completed` event arrives afterwards, `confirm_payment` marks the order paid and queues generation for money that was already returned.
- سيناريو الفشل: Proven with a scratch test: `charge.refunded` (metadata order_id, pi_1) followed by `checkout.session.completed` (pi_1) gives outcomes ['not_refundable', 'paid'] and order status `queued`. Realistic trigger: the webhook endpoint is down or misconfigured for a few hours, customers complain, and support refunds them in Stripe. When the endpoint recovers, the refund events (first attempt) can arrive before the older completed events (later retry). Each of those customers then gets both the refund and the report.
- الإصلاح المقترح: In `confirm_payment`, before marking paid, check whether a refund was already received for this payment: an existing `payment_events` row with `event_type='charge.refunded'` and `data->>'provider_payment_id' = provider_payment_id`, or for the order id. If found, set the order to REFUNDED (outcome `refunded_before_confirmation`) and do not enqueue generation. Alternatively, have `refund_order` record a refunded-payment marker on payable orders that `confirm_payment` honours.

### PAY-05 [medium] Truncated or safety-cut Gemini replies (finish_reason MAX_TOKENS/SAFETY) are accepted as finished report sections
- الملف: `backend/app/generation/jobs.py`:213
- الوصف: `_generate_section` accepts a reply as soon as `count_words(result.text) >= required_words`. `AIResult.finish_reason` is recorded by the Gemini client but never checked. A section is saved permanently as DONE and is never regenerated, even when it was cut off mid-sentence. This matters with `gemini-2.5-flash` (the default), because thinking tokens count against `gemini_max_output_tokens` (8192, which admins can lower to 64).
- سيناريو الفشل: Proven with a scratch test: a client that returns 46 words with `finish_reason='MAX_TOKENS'` produced all 6 sections with status=done after 1 attempt each, and the report would be built from them. In production, a long Arabic prompt plus heavy thinking exhausts the token budget. The customer's paid PDF then contains sections ending mid-sentence, with no re-ask and no admin signal.
- الإصلاح المقترح: Treat any `finish_reason` other than STOP (or None from older SDKs) as a failed attempt: MAX_TOKENS, SAFETY, RECITATION, PROHIBITED_CONTENT, BLOCKLIST, SPII and OTHER. Re-ask exactly as for a short reply, and store the reason in `section.last_error` when attempts run out. Optionally set a `thinking_config` budget, or raise `max_output_tokens` headroom automatically for thinking models.

### PAY-06 [medium] Customers are easily charged twice: old checkout sessions stay open and pending (async) payments show a 'pay' button again
- الملف: `backend/app/orders/service.py`:278
- الوصف: `new_checkout` creates a fresh Stripe session without expiring the previous one, which stays payable for up to 2 h (`CHECKOUT_LIFETIME`). `checkout.session.completed` with `payment_status='unpaid'` (delayed methods) is mapped to IGNORED (stripe_provider.py line 147), and nothing records that a payment is processing. The order page (OrderStatusView.tsx) shows the "Complete payment" button whenever the order is `awaiting_payment`, including 2 minutes after returning with ?paid=1. Any second payment is only logged as `duplicate_payment`, with no alert, and refunding it then triggers PAY-01.
- سيناريو الفشل: A customer pays with a delayed method, so the session completes unpaid. Or a webhook is delayed for more than 2 minutes. The order page then times out the confirmation spinner and offers "Complete payment". The customer pays again by card, which creates session 2 and gets the order paid. The first payment succeeds later and is also captured. The customer is charged twice, and ops are not alerted.
- الإصلاح المقترح: In `new_checkout`, expire the previously stored session (`client.v1.checkout.sessions.expire(old_id)`, ignoring 'already complete/expired' errors). If the old session is already complete, refuse with `payment_processing`. Persist a `payment_processing` flag or status on `checkout.session.completed` with an unpaid status, and have the order page show "payment processing" instead of a pay button. Surface `duplicate_payment` outcomes to ops, through the dashboard counter or an email.

### PAY-07 [low] Expired-lease jobs are reclaimed forever past max_attempts, and orders can stay in 'generating' indefinitely
- الملف: `backend/app/jobs/queue.py`:68
- الوصف: `claim_next` reclaims any `running` job whose lease expired, without checking `attempts < max_attempts`, and increments attempts unconditionally. A job that kills the worker process (OOM, segfault, SIGKILL) is never routed through `mark_failed_attempt`, so it is retried every lease period forever. Separately, `OrderBusyError` is raised by `_order_generation_lock` outside the try block (generation/jobs.py lines 73-74). If the job exhausts its attempts that way, or if the first holder later fails with a stale `is_last_attempt=False`, the job ends FAILED while the order stays `generating`. Nothing ever marks it `generation_failed`.
- سيناريو الفشل: Proven: a job with attempts=5/5, status running and an expired lease was claimed again with attempts=6/5. A Chromium render that pushes the worker over its memory limit and gets the process OOM-killed would loop every 5 minutes, repeatedly taking the worker down. In the lease-overrun case (PDF launch plus render timeouts can exceed 300 s), the customer sees the progress screen forever.
- الإصلاح المقترح: In `claim_next`, mark expired-lease rows with `attempts >= max_attempts` as FAILED (last_error='lease expired after max attempts') instead of claiming them. For `generate_report`, also mark the order `generation_failed`. Move the lock acquisition inside the try in `handle_generate_report`, so an `OrderBusyError` on the last attempt also marks the order.
