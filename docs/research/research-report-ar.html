1. النتيجة الرئيسية

المشروع قابل للتنفيذ بوصفه منصة محتوى وتجارة إلكترونية تنتج قراءة شخصية مستوحاة من الأبراج الغربية والتقاليد الصينية. لكنه يحتاج إلى تثبيت قواعد الحساب، ومواصفات التقرير، ومسار الدفع والتسليم قبل تقدير تكلفة تنفيذ نهائية. أكثر الأجزاء حساسية هي صحة بيانات مكان ووقت الميلاد، وترخيص مكتبة الحساب، ومنع تكرار التوليد بعد إشعارات الدفع، وحماية رابط التقرير.

هذه دراسة للمتطلبات والجدوى؛ المجلد لا يتضمن تطبيقًا أو قاعدة بيانات أو سكريبت حساب يمكن تدقيقه أو اختباره. كما لا تتضمن الملفات أدلة على صلاحية المنتج كاختبار نفسي علمي. الأفضل تقديمه كقراءة ثقافية وتأملية، وتجنب وصف المخرجات بأنها تشخيص أو حقيقة مثبتة عن شخصية المستخدم.

4. المنتج المطلوب كما فهمته من الملفات

الخدمة المجانية

المستخدم يدخل تاريخ الميلاد والبريد واللغة. يحسب Python البرج، ثم تُعرض قراءة محفوظة مسبقًا على الخادم. لا حاجة لاستدعاء Gemini لكل زيارة ما دام المحتوى ثابتًا.

النقطة غير المحسومة: هل المجاني يعرض البرج الغربي فقط، أم الغربي مع حيوان السنة الصينية؟ إذا كان الأول فالمحتوى الأساسي 12 قراءة لكل لغة. وإذا كان دمجًا مستقلًا بين 12 برجًا و12 حيوانًا فقد يصل إلى 144 تركيبة لكل لغة. هذه نتيجة حسابية محتملة وليست مطلبًا مؤكدًا.

تاريخ الميلاد وحده يسمح بتبسيط حساب البرج الشمسي، لكنه لا يحسم جميع الحالات القريبة من لحظة انتقال الشمس بين برجين. يجب وصف القراءة المجانية وفق دقتها الفعلية أو إضافة البيانات اللازمة لتلك الحالات.

الخدمة المدفوعة

المستخدم يدخل يوم وشهر وسنة الميلاد، والساعة والدقيقة، والبلد والمدينة، والبريد. ثم يحسب النظام الشمس والقمر والطالع، ومكونات صينية للسنة والشهر واليوم. بعد تأكيد الدفع تُنفذ ستة برومبتات وتُجمع النتائج في PDF يحمل الهوية، يُتاح تنزيله وتصل رسالة بريد للمستخدم.

الموجز لا يذكر اللغة ضمن قائمة حقول المدفوع، رغم وجود تعدد اللغات في المشروع؛ يجب إضافتها صراحةً إلى الطلب حتى تكون لغة التقرير ورسالة البريد محددة.

الإدارة والمحتوى

المطلوب لوحة لإدارة العروض والخصومات، وسلاسل الكتب المسماة Galaxy Library، والبرومبتات، ومحتوى الصفحات، والمدونة وصفحة المقال. لا يوجد وصف كافٍ لبيع الكتب، أو شحنها، أو تنزيلها، أو تراخيصها. تُفصل هذه الخيارات عن مجرد عرض المكتبة.

اشتراط عدم إنشاء حساب للزائر لا يلغي ضرورة وجود دخول محمي للمشرفين.

5. دقة الحسابات: أهم قرار قبل البرمجة

الأبراج الغربية

يجب اختيار النظام المستخدم: Tropical أو Sidereal، وتعريف أي إعدادات أخرى تظهر في المنتج. لا ينبغي ترك Gemini يقرر الأبراج من تاريخ المستخدم؛ الحساب يتم بمكتبة موثوقة، ثم يستقبل النموذج النتائج المهيكلة ويكتب تفسيرها.

مسار الحساب المقترح:

  1. تحديد المدينة الفعلية وخط العرض والطول.
  2. تحديد منطقة IANA الزمنية المرتبطة بالموقع.
  3. تحويل الوقت المحلي إلى UTC وفق تاريخ الميلاد، بما يشمل القواعد التاريخية والتوقيت الصيفي.
  4. التعامل مع وقت محلي مكرر أو غير موجود عند تغيّر الساعة، بدل قبول قيمة ملتبسة بصمت.
  5. حساب المواقع والطالع وحفظ إصدار مكتبة الحساب وإعداداتها مع الطلب.

توضح IANA أن قاعدة المناطق الزمنية تتضمن التاريخ المحلي وتتغير مع القرارات السياسية وحدود المناطق والتوقيت الصيفي. لذلك لا يكفي تخزين فرق ثابت مثل UTC+3 لكل بلد.

تعديل ضروري: لا نختار العاصمة تلقائيًا عندما يكون للبلد منطقة زمنية واحدة. اشتراك المدن في الوقت لا يعني اشتراكها في الإحداثيات، والطالع يتأثر بالموقع. المطلوب ملف مدن وإحداثيات ومناطق زمنية، لا ربط المدن «حسب البرج».

إذا كان وقت الميلاد مجهولًا، فلا يُعرض طالع محسوب من ساعة افتراضية بوصفه نتيجة دقيقة. يمكن توفير قراءة جزئية مع توضيح حدودها. يجب أيضًا تحديد السنوات التي يدعمها المنتج وكيفية التعامل مع تواريخ قديمة ذات بيانات توقيت أقل يقينًا.

اختيار مكتبة الحساب

Swiss Ephemeris خيار يستحق التقييم، لكن الناشر الرسمي يحدد نظام ترخيص مزدوجًا: AGPL أو ترخيص مهني. وينص على اختيار الترخيص قبل تفعيل خدمة عامة تعتمد المكتبة. لا يكفي كون واجهة Python مجانية لحسم التزامات المشروع.

التوصية: حسم الترخيص والتكلفة مع الناشر قبل الاعتماد النهائي، أو تقييم بديل يناسب متطلبات الدقة والترخيص. هذه ملاحظة مستندة إلى شروط الناشر، وليست حكمًا قانونيًا نهائيًا على بنية تطبيق لم تُبنَ بعد.

التقاليد الصينية

يوضح مرصد هونغ كونغ نظام السيقان والفروع، وأن مكونات السنة والشهر واليوم والساعة تكوّن Eight Characters. وعليه فإن ثلاثة حيوانات وحدها لا تصف جميع مكونات نظام كامل من أربعة أعمدة.

ينبغي تحديد حد انتقال السنة والشهر، والتقويم أو المدرسة المعتمدة، وحد اليوم، ودور ساعة الميلاد، وأي تصحيح للوقت الشمسي. لا تُستنتج حيوانات الشهر واليوم باستعمال رقم الشهر أو اليوم الميلادي بطريقة دورية مرتجلة. المطلوب أمثلة مرجعية متفق عليها مع صاحب المنهج، خصوصًا قرب حدود السنة والشهر واليوم.

6. تصميم رحلة الدفع والتوليد

المسار المقترح:

البيانات ← التحقق والحساب ← طلب محفوظ ← جلسة دفع ← إشعار موثّق ← مهمة خلفية ← توليد وفحص ← PDF ← رابط وبريد

يُحفظ الطلب في قاعدة بيانات بحالة awaiting_payment مع السعر والعملة واللغة وإصدار المحتوى. لا يُحفظ فقط في ذاكرة عملية Python أو جلسة المتصفح. الطلبات غير المدفوعة لها سياسة تنظيف منفصلة.

بعد الدفع، يجب أن يتحقق الخادم من توقيع الإشعار، ومن تطابق المبلغ والعملة والطلب، ومن حالة الدفع الفعلية. إعادة التوجيه إلى صفحة نجاح ليست دليلًا كافيًا على الدفع؛ وبعض الوسائل تؤكد الدفع لاحقًا.

توضح وثائق Stripe أن الإشعارات قد تتكرر أو تصل بغير ترتيب، وأن المعالجة الثقيلة تُوضع في طابور خلفي. لذلك يُسجَّل الحدث ويُمنع إنشاء تقرير جديد لنفس الطلب عند تكراره. Stripe هنا مثال بحثي؛ لم يُحدَّد مزود الدفع في الملفات ولم تُتحقق أهلية حساب التاجر.

حالات الطلب المقترحة:

awaiting_payment → paid → queued → generating → ready

مع حالات مستقلة مثل generation_failed وexpired وrefunded. فشل البريد لا يحوّل تقريرًا جاهزًا إلى تقرير فاشل، وفشل التوليد بعد قبض المبلغ يتطلب مسار إعادة محاولة أو دعم أو استرداد محددًا.

7. مراجعة متطلبات Gemini

الموجز يطلب ستة برومبتات بفاصل 1–2 ثانية وإجمالي يقارب 8 ثوانٍ. هذا ليس ضمانًا يمكن البناء عليه: خمس فواصل وحدها تستهلك 5–10 ثوانٍ، إضافة إلى زمن الاستجابات والتحقق وإنشاء PDF. إذا كانت الاستدعاءات متتابعة فزمنها يتراكم؛ وإذا كانت مستقلة يمكن تقييم تشغيل بعضها بالتوازي ضمن الحصة.

توضح وثائق الحصص حدود الطلبات والتوكنات المرتبطة بالمشروع والنموذج ومستوى الحساب. لذلك إنشاء مفاتيح متعددة للمشروع نفسه ليس حلًا لزيادة الحصة. تؤخذ القيم الفعلية من حساب العميل قبل اختبار الحمل.

الفاصل الثابت لا يدير الحصة وحده. المطلوب طابور، وحد لتزامن الاستدعاءات، ومهلة، وإعادة محاولة بتأخير تصاعدي وتفاوت عشوائي عند أخطاء قابلة للمحاولة. اقتراح أولي: ثلاث محاولات إجمالية لكل جزء، مع حفظ الأجزاء الناجحة وإعادة الجزء الفاشل فقط؛ تُضبط الأرقام بعد قياس الأداء.

شرط «25 كلمة على الأقل» مؤشر محدود. قد تكون الإجابة طويلة لكنها متناقضة، أو ناقصة، أو بلغة أخرى. كما لا يصلح فصل الكلمات بالمسافات وحده لجميع اللغات.

تدعم وثائق المخرجات المهيكلة استخدام JSON Schema. أقترح حقولًا ثابتة للأقسام والعناوين والنص واللغة، يتبعها تحقق من اكتمال الأقسام وصحة اللغة وعدم إعادة اختراع نتائج الحساب. مطابقة البنية لا تُغني عن فحص المعنى.

تحتاج البرومبتات إلى إصدارات ومسودة ومعاينة ونشر. يُحفظ الإصدار المستخدم مع كل طلب، وتُضبط صلاحية تعديله. لا يُرسل البريد للنموذج إذا لم تكن هناك حاجة إليه؛ يمكن إرسال نتائج الحساب واللغة فقط، حسب ما يحتاجه المحتوى فعلًا.

تُظهر صفحة أسعار Gemini اختلاف استخدام المحتوى لتحسين المنتجات بين الفئات المجانية والمدفوعة. يوصى بحساب إنتاج مدفوع ومراجعة شروط الخدمة الخاصة به، مع تقليل البيانات الشخصية المرسلة. الأسعار وأسماء النماذج تتغير؛ لا يتضمن الموجز نموذجًا مختارًا يسمح بتسعير نهائي.

8. التقرير ورابط الأربع والعشرين ساعة

اسم ملف من 64 محرفًا لا يضمن الأمان ما لم يُولَّد بعشوائية آمنة، ويظل جزءًا من حماية متعددة الطبقات. مثال مناسب: 32 بايت عشوائية آمنة ممثلة بـ64 محرفًا ست عشريًا، دون تضمين البريد أو تاريخ الميلاد في الاسم.

التصميم المقترح:

  • التخزين خاص، ولا يوجد مجلد تقارير مفتوح أو قابل للفهرسة.
  • رابط التطبيق يحتوي رمز وصول عالي العشوائية، وتُحفظ بصمته بدل قيمته الخام عند الإمكان.
  • تبدأ مهلة 24 ساعة عند جاهزية التقرير، حتى لا تضيع مدة التنزيل أثناء الانتظار.
  • يتحقق الخادم من الصلاحية عند كل طلب تنزيل، ثم يصدر رابط تخزين قصير العمر لا يتجاوز الوقت المتبقي.
  • يُمنع تسجيل رمز الرابط وبيانات الميلاد في السجلات والتحليلات، وتُضبط سياسة الإحالة والتخزين المؤقت.

توضح AWS أن الرابط الموقّع يمنح الوصول لمن يحمله، وأن انتهاء بيانات الاعتماد قد ينهيه قبل المدة المحددة. لذلك لا يُفترض أن رابطًا مباشرًا من التخزين سيستمر 24 ساعة دائمًا.

هناك فرق بين انتهاء حق الوصول وحذف الملف. الفحص في التطبيق يمنع طلبات التنزيل الجديدة بعد المهلة، أما حذف الكائن والنسخ الاحتياطية فله سياسة منفصلة. ولا يمكن سحب نسخة سبق للمستخدم تنزيلها. كذلك لا يجعل رابط منتهي ملفًا مرفقًا بالبريد منتهيًا؛ إذا كان تقييد التنزيل مقصودًا، فترسل الرسالة رابطًا بدل المرفق.

أي شخص يملك الرابط قد يستخدمه قبل انتهاء الصلاحية. إذا أراد العميل حماية مرتبطة بمالك البريد، يمكن إضافة رمز تحقق بالبريد دون إنشاء حساب دائم.

قالب Word الفارغ يصلح كمرجع بصري، لكنه لا يحدد وحده آلية إنتاج PDF. يمكن تقييم قالب HTML/CSS مع Chromium للحصول على صفحات عربية واتجاه RTL وخطوط مضمّنة، ثم فحص العينات الطويلة والقصيرة بكل لغة قبل الاعتماد. لا تُعرض مخرجات النموذج كـHTML موثوق دون معالجة.

10. الحجم والأداء والتكلفة

ألف مستخدم يوميًا يعادل تقريبًا 0.012 مستخدم في الثانية كمعدل موزع على اليوم، لكنه لا يصف الذروة. ومئة مستخدم متصلين لا تعني مئة عملية توليد مدفوعة في اللحظة نفسها. يجب قياس نسبة الشراء وتوزيع الزيارات وعدد استدعاءات النموذج.

سيناريو تخطيطي فقط: 1,000 زيارة يومية وتحويل 5% ينتجان 50 تقريرًا و300 استدعاء يوميًا عند ستة استدعاءات للتقرير، قبل الإعادات. أما دخول 100 طلب مدفوع دفعة واحدة فقد يولّد 600 استدعاء؛ هذا يحتاج طابورًا وفحص الحصة، ولا يضمن الفاصل القصير نجاحه.

معادلة تكلفة النموذج لكل تقرير:

(توكنات الإدخال ÷ 1,000,000 × سعر الإدخال) + (توكنات الإخراج المحتسبة ÷ 1,000,000 × سعر الإخراج)

ثم تضاف الإعادات وأي بنود فوترة أخرى خاصة بالنموذج. مثال افتراضي غير مقتبس كسعر حالي: 6,000 توكن إدخال و12,000 إخراج، عند سعرَي 1 و5 دولارات للمليون، تعطي 0.066 دولار للتقرير. لا يدخل فيه الدفع والبريد والتخزين والاستضافة والضرائب والدعم والترخيص.

تُقدَّر الربحية بعد قياس تقارير فعلية: سعر البيع ناقص تكلفة التوليد والدفع والتشغيل والاستردادات والتسويق. لا توجد في الملفات أسعار أو ميزانية أو بيانات تحويل تسمح بتقدير ربح موثوق.

اختبار الحمل المطلوب يغطي زيارة المحتوى، وإرسال المجاني، والدفع، وطابور التوليد كلًا على حدة، مع قياس أزمنة الاستجابة ونسبة الأخطاء وتراكم الطابور. يُحدد هدف زمن التسليم بعد النموذج الأولي بدل وعد ثابت بثماني ثوانٍ.

11. الهوية والمنافسة والمحتوى

الشعار يعطي انطباعًا احتفاليًا وفخمًا، ويعبّر التنين والرموز عن فكرة الدمج. لكنه كثيف التفاصيل في المقاسات الصغيرة؛ يوصى بنسخة مبسطة للأيقونة، ونسخة أفقية للترويسة، مع الاحتفاظ بالأصل للتقرير. الذهبي مناسب للهوية، ولا يُعتمد للنصوص الصغيرة على الأبيض قبل فحص التباين. الألوان الإضافية المقترحة مثل الكحلي الداكن والعاجي خيارات تصميمية وليست مستخرجة من الملف.

يعرض Astrodienst قراءات مجانية، وحسابات خرائط، ومنتجات تحليل متقدمة. وجود هذه العروض يعني أن «قراءة أبراج عامة» وحدها ليست تميزًا كافيًا. التميز المحتمل لـZodiac Blend هو وضوح منهج الدمج، وجودة اللغة والتقرير، وتجربة شراء سهلة وشفافة. هذه قراءة سوقية أولية من نموذج منافس، وليست مسحًا كميًا للسوق أو إثباتًا للطلب.

قبل التوسع، يُختبر التقرير على عينة صغيرة: هل يقدم محتوى مختلفًا عن المجاني؟ هل يفهم القارئ أسباب النتائج وحدودها؟ هل يراه مستحقًا للسعر؟ يجب مراجعة الترجمات بواسطة محرر، وتوحيد المصطلحات الغربية والصينية.

في المدونة، تُفضَّل مقالات أصلية عن المنهج وفهم الخريطة والفرق بين الأنظمة. نشر نصوص كثيرة مولّدة دون مراجعة قد ينتج تكرارًا وأخطاء. Galaxy Library تحتاج تعريفًا لمحتواها وحقوق استخدام الكتب وصورها وطريقة الوصول إليها.

12. الخصوصية والإدارة

البريد وتاريخ ووقت ومكان الميلاد بيانات شخصية. المطلوب تحديد الغرض ومدة الاحتفاظ وما يصل إلى مزود الذكاء الاصطناعي والبريد والدفع، ووضع سياسة مكتوبة تناسب الأسواق المستهدفة. لم تُحدد الأسواق أو الأعمار في الملفات، لذلك لا يمكن حسم الالتزامات القانونية والضريبية حسب البلدان ضمن هذه الدراسة.

لا يُعتبر إدخال البريد لطلب التقرير موافقة تلقائية على الرسائل التسويقية. يُفصل اشتراك التسويق عن رسائل الطلب. ويُحدد التعامل مع طلب حذف البيانات، وتقليل بيانات السجلات، وحذف الطلبات المهجورة.

لوحة الإدارة تحتاج MFA، وصلاحيات حسب الدور، وسجل تغييرات للبرومبتات والخصومات. تُخزن أسرار الخدمات في بيئة الخادم، ولا تُعرض في الواجهة. التكامل مع «جارفيس» غير محدد بما يكفي: يحتاج اسم الخدمة وواجهتها وصلاحياتها، ولا يُعد شرطًا لبناء النسخة الأساسية ما لم يثبته العميل.

14. خطة تنفيذ مقترحة ومعايير قبول

المرحلة الأولى: تثبيت المواصفات. اعتماد المنهج، والعينة، واللغات، والترخيص، والدفع، والخصوصية. المخرج: مواصفات قابلة للاختبار بدل قائمة عامة.

المرحلة الثالثة: تجربة المدفوع في بيئة اختبار. الحساب التفصيلي، الدفع التجريبي، الطابور، البرومبتات، PDF، والبريد. لا يُعاد حساب أو توليد الطلب عند تحديث الصفحة.

المرحلة الرابعة: المحتوى والإطلاق. العروض والخصومات والمدونة والمكتبة وفق النطاق المتفق عليه، ثم اختبار الحمل والتسليم والاستعادة وإطلاق مراقب.

معايير قبول أساسية:

  1. تطابق نتائج الحساب مع أمثلة مرجعية تشمل حدود الانتقال والتوقيت الصيفي.
  2. تكرار إشعار الدفع لا يسبب توليدًا أو تسليمًا مكررًا غير مقصود.
  3. لا يتولد المدفوع لعملية غير مؤكدة أو مبلغ غير مطابق.
  4. يمكن استكمال الأجزاء الفاشلة دون خسارة الأجزاء الناجحة.
  5. PDF مقروء بكل لغة، والترويسة والتذييل لا يتداخلان مع النص.
  6. ينتهي الوصول في موعده، ولا يوجد وصول عام عبر عنوان التخزين.
  7. يبقى التقرير جاهزًا إذا تعذر البريد، مع إعادة إرسال قابلة للتتبع.
  8. لا يؤدي تعديل البرومبت إلى تغيير سجل الإصدار المستخدم لطلب سابق.
  9. يحتفظ النظام بحالة الطلب بعد إعادة تشغيل الخدمة أو تعطل العامل.
  10. تمر سيناريوهات الحمل المتفق عليها ضمن أهداف أداء مقاسة.

هذه معايير مقترحة لم تُنفذ اختبارات لها، لأن المجلد لا يحتوي تطبيقًا.

لماذا PostgreSQL هي اختياري؟

المشروع يحتوي بيانات مترابطة: طلب له دفعات وحساب فلكي وإصدار برومبت وأقسام تقرير وملف وصلاحية وصول. PostgreSQL تناسب هذا النموذج، وتدعم المعاملات والعلاقات والقيود والفهارس، مع إمكانية حفظ النتائج المتغيرة في JSONB.

توضح وثائق PostgreSQL مستويات عزل المعاملات؛ لكن اختيار القاعدة وحده لا يمنع سباق إشعارَي دفع. التطبيق يحتاج معاملات وقيودًا فريدة وقفلًا مناسبًا للسجل عند الانتقال إلى حالة مدفوعة أو بدء التوليد.

MySQL بديل صالح إذا كان الفريق متخصصًا به. لا أرى في الملفات حاجة تجعل MongoDB أفضل كقاعدة رئيسية، أو تستدعي تخزين جميع البيانات كوثائق. Redis تستخدم لبيانات مؤقتة والطابور، بينما يظل سجل الطلب والدفع والحالة في PostgreSQL. SQLite مناسبة لتجربة محلية محدودة، وأوصي بـPostgreSQL أيضًا في بيئة التطوير لتقليل الاختلاف عن الإنتاج.

Redis المخصصة لوسيط المهام تُضبط لمنع إخلاء الرسائل بسبب ضغط الذاكرة، مع سياسة استمرارية مناسبة؛ يُفضَّل فصلها عن Redis الخاصة بالكاش القابل للإخلاء. يتيح سجل outbox في PostgreSQL معالجة فجوة حفظ الطلب ثم نشر المهمة، وإعادة إرسال العمل المفقود دون إنشاء تقرير جديد.

الطوابير: لماذا أعدّل اقتراح Redis؟

توصي FAQ الخاصة بـCelery بـRabbitMQ أو وسيط AMQP عندما تكون متطلبات الموثوقية صارمة. وبما أن الدفع يسبق إنتاج التقرير، فأنا أميل إلى Celery + RabbitMQ للنسخة المدفوعة متى كان تشغيله متاحًا. Redis تظل خيارًا مشروعًا وأبسط في بعض الاستضافات.

تذكر وثائق Celery مع Redis أن تجاوز visibility timeout قد يؤدي إلى إعادة تسليم المهمة، وأن التأخير الطويل للمهمة يحتاج عناية. لذلك لا نترك مهمة تنظيف تنتظر داخل الطابور 24 ساعة؛ نحفظ expires_at ونشغّل فحصًا دوريًا، بينما يمنع التطبيق التنزيل فور انتهاء المهلة.

تشرح RabbitMQ quorum queues تأكيد النشر واستمرارية الرسائل وحدودها عند فشل العقد. الاستفادة من التكرار العالي تتطلب إعدادًا متعدد العقد أو خدمة مُدارة مناسبة؛ تثبيت RabbitMQ على خادم واحد لا يوفر تلك الحماية تلقائيًا. وتوثّق Celery إعدادات quorum queues وتأكيد النشر.

أي وسيط لا يضمن وحده تنفيذ الأثر الخارجي مرة واحدة. نحتاج معرف طلب ثابتًا وقيودًا وقفلًا أو lease، وسجل أجزاء التقرير، وoutbox لإرسال العمل بعد حفظه، ومسار استعادة. قد ينتهي استدعاء النموذج بمهلة دون أن نعرف هل عالجه المزود؛ إعادة المحاولة قد تضيف تكلفة حتى إذا منعنا اعتماد تقريرين لنفس الطلب.

متطلبات العميل تشمل محتوى الصفحات والمدونة والترجمات والكتب. إذا كان يقصد تعديل نصوص في حقول محددة فقط، تكفي Django Admin مخصصة. وإذا كان يحتاج معاينة وتركيب أقسام الصفحة وتجربة تحرير للمحتوى متعدد اللغات، أوصي بتقييم Wagtail ضمن نفس المشروع.

تُثبت إصدارات Python والإطار والمكتبات وChromium بعد فحص التوافق. Django 5.2 إصدار LTS بحسب وثائقه؛ يمكن اختياره إن وافق تبعيات المشروع، أو اختيار إصدار مدعوم آخر مع خطة تحديث. قالب GitHub الذي يستخدم إصدارًا أحدث لا يفرض علينا استخدامه دون هذا الفحص.

الإنتاج المقترح Linux وحاويات Linux. توضح Celery FAQ أن Windows غير مدعوم رسميًا منذ Celery 4. يمكن تطوير المشروع على جهاز Windows مع تشغيل العمال داخل بيئة Linux مناسبة؛ وجود Windows في مجلد العمل لا يحدد نظام الاستضافة.

متى أغيّر التوصية؟

أختار FastAPI وواجهة React إذا ثبت أن الفريق أكثر خبرة بهما أو أن API وتطبيق الهاتف هما الأساس. أختار Laravel إذا كان الفريق متخصصًا به ويمكنه تشغيل الحسابات دون تعقيد غير لازم. أختار Next.js عندما تكون React ومتطلبات واجهتها سببًا واضحًا، وأختار طابور PostgreSQL بعد نموذج تكامل وفشل ناجح إذا كانت إزالة الوسيط هدفًا مهمًا.

أما مع المتطلبات الموجودة وحدها، فأفضل قرار حالي هو Django + PostgreSQL، مع Wagtail حسب حاجة التحرير، وCelery وعمال منفصلين، وRabbitMQ للموثوقية الصارمة أو Redis مخصصة كبداية أبسط. يُحفظ السجل الدائم واستعادة العمل في PostgreSQL في الحالتين، وتثبت قدرة 500 مستخدم بقياس لا بتسمية التقنية.
