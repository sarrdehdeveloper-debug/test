## 18. مراجعة الاختيار بعد البحث في GitHub والتوثيق الرسمي

### الحكم النهائي

تاريخ المراجعة: 5 أكتوبر 2026. أبقي على Django وPostgreSQL كأساس أنسب لهذا المشروع وفق المتطلبات الحالية، وأحسّن الاختيار في إدارة المحتوى ووسيط المهام. هذا حكم هندسي مبني على الملاءمة وتكلفة التنفيذ والتشغيل؛ ليس إثباتًا أن هذه البنية الأسرع في كل الحالات، أو أنها ستتحمل 500 مستخدم على أي استضافة.

البنية المفضلة للنسخة المدفوعة عند توفر ميزانية تشغيل مناسبة: Python + Django، وPostgreSQL، وCelery مع RabbitMQ، وRedis للكاش، وتخزين خاص متوافق مع S3، وصفحات Django مع CSS وTypeScript. يُضاف Wagtail عندما يحتاج العميل تحرير الصفحات والمدونة والترجمات بمعاينة ومسار نشر؛ ولا يلزم أن تصبح الواجهة Headless أو React لاستخدامه.

إذا كان المطلوب تقليل الخدمات والتكلفة الأولية، يظل Celery مع Redis مخصصة للطابور، منفصلة عن الكاش، خيارًا مقبولًا مع outbox واستعادة ومراقبة. الانتقال إلى RabbitMQ لا يفرضه عدد الزوار وحده؛ أساسه متطلبات موثوقية العمل المدفوع وقدرة الفريق على التشغيل.

### ماذا شمل البحث؟

قورنت مستودعات وقوالب Django وFastAPI، وأدوات Celery وDramatiq وRQ وPgQueuer، وWagtail، ومكتبات الحساب الصينية والغربية. قُرئت وثائق Django وFastAPI وNext.js وLaravel وPostgreSQL وMySQL وMongoDB وRabbitMQ وSupabase وPgBouncer، ومواد أدوات PDF. استُخدمت GitHub API للتحقق من حالة الأرشفة وتاريخ آخر commit على الفرع الافتراضي في 11 مستودعًا؛ البيانات محفوظة في ملف GitHub Research - 2026-10-05.json بجانب التقرير.

القراءة شملت README والتوثيق وملفات ترخيص مختارة، وليست تدقيقًا أمنيًا شاملًا لكل الكود والتبعيات. آخر commit قد يكون تحديث توثيق أو تبعية، ولا يثبت وحده جودة المكتبة. لم تُستخدم النجوم لترتيب الحلول، ولم يُنفذ benchmark لتطبيق لم يُبنَ بعد.

### مقارنة الأطر لهذا المشروع

| الحل | نقاط القوة ذات الصلة | التكلفة أو القيد | قراري |
|---|---|---|---|

| FastAPI + React | مناسب لـAPI وواجهة تفاعلية وفريق يفصل الواجهة عن الخادم. | يلزم اختيار وإكمال CMS وإدارة تشغيلية وتكامل الواجهة والطابور. | بديل قوي إذا كان API أو تطبيق الهاتف محور المنتج، أو لدى الفريق خبرة جاهزة. |
| Next.js + Python workers | واجهة React وصفحات خادمية/ثابتة، مع إبقاء الحسابات في Python. | حدود بين Node وPython، وطابور وCMS، وإعدادات تنسيق الكاش عند تعدد النسخ. | مناسب لفريق TypeScript/React؛ لا أجعله شرطًا لحمل 500 زائر. |
| Laravel + PostgreSQL + Python | منظومة ويب وطوابير جيدة، خاصةً لفريق PHP. | تشغيل وتكامل PHP مع مكونات Python إن احتفظنا بالحسابات فيها. | قد يكون أفضل اقتصاديًا لفريق Laravel قوي؛ لا يوجد دليل أنه غير قادر على الحمل. |

يدعم [قالب FastAPI الرسمي](https://github.com/fastapi/full-stack-fastapi-template) PostgreSQL وReact وTypeScript وVite وDocker واختبارات، ويستخدم SQLModel. وجود قالب كامل لا يعني أنه يحتوي CMS أو سير التقارير المطلوب؛ يجب تقييم الفجوة من متطلباتنا. استنتاج أن Django أوفر هنا مرتبط بهذه الفجوة، وليس بمقارنة سرعة لغة بلغة.

تشرح [وثائق Next.js للاستضافة الذاتية](https://nextjs.org/docs/app/guides/self-hosting) اعتبارات تعدد النسخ والكاش المشترك والتنسيق بين النسخ. هذه تكلفة إعداد إضافية يمكن إدارتها، وليست عيبًا يمنع استخدام الإطار.

وتعرض [وثائق Laravel](https://laravel.com/docs/13.x/queues) خيارات الطوابير ومعالجة المهام، لذلك لا أستبعده بسبب الأداء. اختيار خبرة الفريق يقلل مخاطر التنفيذ، وقد يتفوق على توفير نظري في عدد المكونات.

### قاعدة البيانات: هل PostgreSQL أفضل فعلًا؟

نعم، هي اختياري الأول لهذا النموذج من البيانات، لا لأن 500 شخص يتطلبون قاعدة بعينها. الطلب والدفع والخصم والتقرير علاقات منظمة، والنتائج الفلكية وأقسام النموذج يمكن وضع الأجزاء المرنة منها في JSONB. توضح [وثائق PostgreSQL](https://www.postgresql.org/docs/current/datatype-json.html) خصائص JSONB وفهرسته.

| الخيار | التقييم |
|---|---|
| PostgreSQL مُدارة | الاختيار الأساسي: العلاقات والمعاملات والقيود وJSONB، مع تخفيف عمل النسخ الاحتياطي والتشغيل. |
| MySQL / InnoDB | بديل صالح؛ [InnoDB](https://dev.mysql.com/doc/refman/8.4/en/innodb-introduction.html) يدعم المعاملات والقفل على مستوى الصف. لا أزعم أن PostgreSQL أسرع منه في كل حمل. |
| MongoDB | يدعم [معاملات ACID](https://www.mongodb.com/docs/manual/core/transactions/)، لكن نموذج المشروع لا يقدم سببًا واضحًا للتحول عن العلاقات SQL. |
| Supabase | خيار استضافة وخدمات مبني على PostgreSQL، وليس محرك قاعدة مختلفًا. يُقارن بمزود PostgreSQL مُدار آخر حسب الموارد والنسخ الاحتياطي والمنطقة والكلفة. |
| Redis | للكاش أو وسيط المهام بحسب التصميم؛ لا يكون المصدر الدائم الوحيد للطلبات المدفوعة. |

تحذر [وثائق Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres) من اختلاف خصائص أنماط الاتصال، ومنها قيود transaction pooling على حالة الجلسة وLISTEN/NOTIFY وprepared statements في خدمتها. كما توضح [PgBouncer](https://www.pgbouncer.org/features.html) فروق أوضاع pooling. لا نفعّل pooling عشوائيًا ثم نفترض توافق كل ميزة معه؛ يختبر إعداد ORM وطريقة الاتصال الفعلية.

### الطوابير: لماذا أعدّل اقتراح Redis؟

توصي [FAQ الخاصة بـCelery](https://docs.celeryq.dev/en/stable/faq.html) بـRabbitMQ أو وسيط AMQP عندما تكون متطلبات الموثوقية صارمة. وبما أن الدفع يسبق إنتاج التقرير، فأنا أميل إلى Celery + RabbitMQ للنسخة المدفوعة متى كان تشغيله متاحًا. Redis تظل خيارًا مشروعًا وأبسط في بعض الاستضافات.

تذكر [وثائق Celery مع Redis](https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/redis.html) أن تجاوز visibility timeout قد يؤدي إلى إعادة تسليم المهمة، وأن التأخير الطويل للمهمة يحتاج عناية. لذلك لا نترك مهمة تنظيف تنتظر داخل الطابور 24 ساعة؛ نحفظ expires_at ونشغّل فحصًا دوريًا، بينما يمنع التطبيق التنزيل فور انتهاء المهلة.

تشرح [RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues) تأكيد النشر واستمرارية الرسائل وحدودها عند فشل العقد. الاستفادة من التكرار العالي تتطلب إعدادًا متعدد العقد أو خدمة مُدارة مناسبة؛ تثبيت RabbitMQ على خادم واحد لا يوفر تلك الحماية تلقائيًا. وتوثّق [Celery](https://docs.celeryq.dev/en/stable/userguide/configuration.html) إعدادات quorum queues وتأكيد النشر.

أي وسيط لا يضمن وحده تنفيذ الأثر الخارجي مرة واحدة. نحتاج معرف طلب ثابتًا وقيودًا وقفلًا أو lease، وسجل أجزاء التقرير، وoutbox لإرسال العمل بعد حفظه، ومسار استعادة. قد ينتهي استدعاء النموذج بمهلة دون أن نعرف هل عالجه المزود؛ إعادة المحاولة قد تضيف تكلفة حتى إذا منعنا اعتماد تقريرين لنفس الطلب.

| أداة المهام | سبب النظر فيها | موقفي |
|---|---|---|
| Celery | التكامل مع Django، وتوجيه الطوابير، والإعادات، والمراقبة، وإمكانية توزيع مراحل العمل. | اختياري هنا، مع إبقاء حالة المنتج في PostgreSQL. |
| Dramatiq | بديل يستحق نموذجًا صغيرًا إذا كان الفريق يعرفه؛ له تكامل Django. | صالح، ولا يوجد في هذه الدراسة benchmark يثبت أنه أسرع أو أوثق في هذا الحمل. |
| RQ / Django-RQ | واجهة تشغيل أبسط لمهام Python عبر Redis. | قد يكفي إذا أصبح المسار مهمة واحدة أبسط؛ يحتاج أيضًا idempotency واستعادة. |
| PgQueuer | يحتفظ بالعمل داخل PostgreSQL ويمكن نشره داخل معاملة البيانات. | يقلل وسيطًا خارجيًا، لكنه يحتاج فحص تكامل Django وموارد القاعدة والاتصالات والميزات المطلوبة. |
| Django Tasks | API لتعريف العمل في Django الحديثة. | ليست وحدها عامل تنفيذ إنتاجيًا؛ تحتاج backend وعمالًا. |

توضح [وثائق Django Tasks](https://docs.djangoproject.com/en/6.0/ref/tasks/) أن التنفيذ الفعلي متروك لبنية خارجية، وأن backends المدمجة للتطوير والاختبار. وتعرض [FastAPI](https://fastapi.tiangolo.com/tutorial/background-tasks/) Celery خيارًا للعمل الثقيل في عمليات أو خوادم مختلفة. لذلك لا نخلط دعم async مع طابور دائم يستعيد التقارير المدفوعة بعد إعادة التشغيل.

### إدارة المحتوى: Wagtail أم Django Admin؟

متطلبات العميل تشمل محتوى الصفحات والمدونة والترجمات والكتب. إذا كان يقصد تعديل نصوص في حقول محددة فقط، تكفي Django Admin مخصصة. وإذا كان يحتاج معاينة وتركيب أقسام الصفحة وتجربة تحرير للمحتوى متعدد اللغات، أوصي بتقييم Wagtail ضمن نفس المشروع.

يوضح [توثيق Wagtail على GitHub](https://github.com/wagtail/wagtail/blob/main/docs/advanced_topics/i18n.md) إدارة المحتوى حسب اللغة وخيارات إدارة ترجماته. الاستنتاج هنا أن استخدام CMS قائم قد يوفر تطوير محرر محتوى خاص. وهو لا يترجم المحتوى تلقائيًا إلى كل اللغات بمجرد تثبيته، ولا يعالج البرومبتات والمدفوعات تلقائيًا.

يوزع العمل بحيث يدير Wagtail المحتوى التحريري، وتدير وحدات Django الطلبات والبرومبتات والدفع. لا أضيف CMS ثانية منفصلة أو قاعدة إضافية لهذا السبب وحده.

### الحسابات والتراخيص: ما الذي لا يحله اختيار إطار الويب؟

يدعم [lunar-python](https://github.com/6tail/lunar-python) التقويم الصيني وعددًا من مكوناته؛ وجود المكتبة لا يحدد تلقائيًا مدرسة الحساب أو حدود السنة واليوم والساعة المطلوبة من العميل. تؤخذ نتائجها عبر طبقة مستقلة، وتختبر ضد أمثلة معتمدة قرب الحدود.

يحتوي [ملف ترخيص pyswisseph](https://github.com/astrorigin/pyswisseph/blob/master/LICENSE.txt) على AGPL. ويشرح [ناشر Swiss Ephemeris](https://www.astro.com/swisseph/swephinfo_e.htm) الترخيص المهني للنواة. لا أفترض أن شراء ترخيص النواة يحسم تلقائيًا شروط واجهة Python وكل أغلفتها؛ يلزم اختيار ربط وترخيص مناسبين. تغيير Django إلى Next.js أو Laravel لا يزيل هذه المسألة.

### PDF والإصدارات ونظام التشغيل

راجعت [Playwright Python](https://github.com/microsoft/playwright-python) و[WeasyPrint](https://github.com/Kozea/WeasyPrint). يبقى HTML/CSS مع Chromium عبر Playwright مرشحًا جيدًا لتوحيد تصميم التقرير، وWeasyPrint مرشحًا آخر لتقييم مستندات الطباعة. لا أحسم الأفضل للعربية دون عينات من التقرير الحقيقي وقياس الذاكرة وزمن الإنشاء والخطوط وفواصل الصفحات.

تُثبت إصدارات Python والإطار والمكتبات وChromium بعد فحص التوافق. [Django 5.2](https://docs.djangoproject.com/en/5.2/releases/5.2/) إصدار LTS بحسب وثائقه؛ يمكن اختياره إن وافق تبعيات المشروع، أو اختيار إصدار مدعوم آخر مع خطة تحديث. قالب GitHub الذي يستخدم إصدارًا أحدث لا يفرض علينا استخدامه دون هذا الفحص.

الإنتاج المقترح Linux وحاويات Linux. توضح [Celery FAQ](https://docs.celeryq.dev/en/stable/faq.html) أن Windows غير مدعوم رسميًا منذ Celery 4. يمكن تطوير المشروع على جهاز Windows مع تشغيل العمال داخل بيئة Linux مناسبة؛ وجود Windows في مجلد العمل لا يحدد نظام الاستضافة.

### هل البنية تستطيع خدمة 500 زائر؟

لا يقدم أي مستودع أو README شهادة بأن تطبيقنا سيتحمل 500 زائر. تدعم البنية الفصل والتوسع المطلوبين، لكن القبول النهائي مرتبط بسيناريوهات الحمل والبيئة الفعلية، بما فيها بطء قاعدة البيانات واستجابات الخدمات الخارجية.

خطة الإثبات تبقى اختبار 500 مستخدم برحلات واقعية وذروة أعلى، ثم اختبار طلبات مدفوعة متزامنة منفصل. نضيف اختبارات تعطل العامل بعد استدعاء النموذج، وتعطل الوسيط بعد حفظ الدفع، وإشعارات مكررة، وفشل PDF أو البريد. تقاس سرعة صفحات الويب منفصلة عن انتظار التوليد وتكلفته.

يمكن استخدام نتائج [TechEmpower](https://www.techempower.com/benchmarks/) لفهم سيناريوهات عامة، لكن لا يجوز تحويل ترتيب اختبار JSON أو استعلام صغير إلى حكم على رحلة تتضمن حسابًا ودفعًا وستة برومبتات وPDF. لا توجد في هذه الدراسة أرقام أداء تجريبية لبنية Zodiac Blend.

### متى أغيّر التوصية؟

أختار FastAPI وواجهة React إذا ثبت أن الفريق أكثر خبرة بهما أو أن API وتطبيق الهاتف هما الأساس. أختار Laravel إذا كان الفريق متخصصًا به ويمكنه تشغيل الحسابات دون تعقيد غير لازم. أختار Next.js عندما تكون React ومتطلبات واجهتها سببًا واضحًا، وأختار طابور PostgreSQL بعد نموذج تكامل وفشل ناجح إذا كانت إزالة الوسيط هدفًا مهمًا.

أما مع المتطلبات الموجودة وحدها، فأفضل قرار حالي هو Django + PostgreSQL، مع Wagtail حسب حاجة التحرير، وCelery وعمال منفصلين، وRabbitMQ للموثوقية الصارمة أو Redis مخصصة كبداية أبسط. يُحفظ السجل الدائم واستعادة العمل في PostgreSQL في الحالتين، وتثبت قدرة 500 مستخدم بقياس لا بتسمية التقنية.
